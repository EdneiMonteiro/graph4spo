🌐 Graph API vs REST / ACS — por que Graph?

CritérioSharePoint REST API (/_api)Azure Cognitive Search connector (ACS)Microsoft Graph API
Autenticação Cookie / token SPO — depende de contexto do site App Registration com Sites.Read.All ou admin cred ✅ SP ou MI — standardizado
Escopo mínimo ❌ Não suporta Sites.Selected ❌ Exige Sites.ReadAll ou SharePoint admin ✅ Sites.Selected — por site
Metadados de lista Disponível via /_api/web/lists mas endpoint diferente Mapeamento parcial, configuração manual ✅ $expand=listItem($expand=fields) — nativo
Download de arquivo /_api/web/GetFileByUrl — URL dependente do site Via indexador — não dá controle granular ✅ /drives/{id}/items/{id}/content ou @downloadUrl
Suporte a MI ❌ Sem suporte nativo a MI ⚠️ Parcial via indexer MI ✅ Nativo — ManagedIdentityCredential
Evolução / suporte Legado — Microsoft não investe mais Dependente do conector ACS ✅ Produto principal — todas as novidades
Conclusão: SHA REST é legado. ACS connector é uma caixa preta sem controle de escopo. Graph API é o único que suporta Sites.Selected + MI + metadados em uma chamada.
Identidade

🆚 Service Principal vs Managed Identity

🔐 Service Principal

  • Objeto no Entra ID criado a partir de um App Registration
  • Você gerencia a credencial: client secret ou certificado
  • Funciona em qualquer runtime: local, CI/CD, on-prem, Azure
  • Pode autenticar em tenants diferentes (cross-tenant)
  • Credencial tem expiração — requer rotação

🪪 Managed Identity

  • Identidade gerenciada pelo Azure — sem credencial
  • Token obtido automaticamente via endpoint IMDS da plataforma
  • Só funciona em recursos Azure com suporte: VM, Container Apps, Functions, AKS
  • Requer que Azure e SharePoint estejam no mesmo tenant Entra ID
  • Completamente passwordless — zero rotação
Seu cenário (SPO + Azure, mesmo tenant):
Os dois funcionam. A escolha depende de onde o código roda e se há outros tenants envolvidos.

Segurança

🔒 Mínimo privilégio — Sites.Selected

PermissãoEscopo efetivoRecomendada?
Sites.ReadWrite.AllTodos os sites, escrita❌ Nunca
Sites.Read.AllTodos os sites, leitura❌ Evitar
Sites.SelectedSó sites explicitamente autorizados✅ Sempre
Sites.Selected ≠ acesso automático. Ter o App Role não dá acesso a nada — é preciso fazer um segundo passo: autorizar explicitamente cada site (Slide 8).

Granularidade na prática

  • O grant é por site collection — não por biblioteca individual
  • Se precisar isolar acesso a uma biblioteca específica:
    → Crie um site separado apenas para essa biblioteca
    → Conceda o grant apenas nesse site
  • Roles disponíveis: "read", "write", "manage", "fullControl"
  • Para RAG (somente leitura): sempre "read"
Princípio: um site collection, um grant, um propósito. Se o app não precisa escrever, não dê write. Se precisar de apenas um site, não use Sites.Read.All.
Decisão

🧭 Qual é o melhor? SP vs MI — recomendação

🔐 Prefira Service Principal quando:

  • Código roda fora do Azure (local, on-prem, CI/CD externo)
  • O tenant do SharePoint é diferente do tenant Azure
  • Precisa de um Client ID portátil (usar o mesmo SP em múltiplos ambientes)
  • Time precisa auditar e controlar a credencial explicitamente
Segurança obrigatória: use sempre certificado, nunca client secret. Guarde o certificado no Key Vault.

🪪 Prefira Managed Identity quando:

  • Código roda em Azure: Container App, VM, Function, AKS
  • SPO e Azure no mesmo tenant Entra ID
  • Zero tolerância para rotação de chaves
  • Arquitetura passwordless é requisito de segurança
  • Prefira User-Assigned para poder fazer grants antes do deploy
Produção em Azure: MI é sempre superior — elimina toda a superfície de ataque por credencial vazada.

Service Principal

🛡️ SP: por que certificado, nunca client secret

Client SecretCertificado
FormatoString — pode aparecer em log, env, gitPar de chaves — chave privada nunca sai do KV
Vazamento❌ Alta superfície — qualquer print/log✅ Bytes PFX em memória, efêmero
RotaçãoManual — fácil de esquecerData de expiração visível no KV
Recomendação MSApenas para testes✅ Apps não-interativas em produção
Nunca coloque o client secret em uma variável de ambiente do Container App ou em um arquivo .env versionado. 
# 1. Gerar certificado direto no Key Vault
az keyvault certificate create \
  --vault-name kv4spo \
  --name sp4spo-cert \
  --policy "$(az keyvault certificate \
      get-default-policy)"

# 2. Exportar .cer (público) para registrar no SP
az keyvault certificate download \
  --vault-name kv4spo \
  --name sp4spo-cert \
  --file sp4spo.cer --encoding DER

# 3. Vincular ao App Registration
az ad app credential reset \
  --id <APP_ID> \
  --cert @sp4spo.cer \
  --append

# No código: KV salva PFX automaticamente como secret
secret = kv.get_secret("sp4spo-cert")
cert   = base64.b64decode(secret.value)
cred   = CertificateCredential(
    tenant_id=tenant_id, client_id=client_id,
    certificate_data=cert)
Entra ID

🔑 Permissões no Entra ID — como configurar

Para Service Principal

# 1. App Registration
az ad app create --display-name sp4spo \
  --sign-in-audience AzureADMyOrg

# 2. Service Principal
az ad sp create --id <APP_ID>

# 3. Adicionar App Role Sites.Selected
#    Graph: 00000003-0000-0000-c000-000000000000
#    Role:  883ea226-0bf2-4a8f-9f9d-92c9162b76e3
az ad app permission add \
  --id <APP_ID> \
  --api 00000003-0000-0000-c000-000000000000 \
  --api-permissions \
    883ea226-0bf2-4a8f-9f9d-92c9162b76e3=Role

# 4. Admin Consent (requer Global Admin)
az ad app permission admin-consent \
  --id <APP_ID>

Para Managed Identity

# Sem App Registration — MI já é um SP no tenant
# Precisamos atribuir o App Role diretamente via Graph

GRAPH_SP=$(az ad sp show \
  --id 00000003-0000-0000-c000-000000000000 \
  --query "{id:id, roleId:appRoles[?value=='Sites.Selected'].id|[0]}" \
  -o json)
GRAPH_ID=$(echo $GRAPH_SP | jq -r '.id')
ROLE_ID=$(echo $GRAPH_SP | jq -r '.roleId')
MI_OID="<principalId da UAMI>"
TOKEN=$(az account get-access-token \
  --resource https://graph.microsoft.com \
  --query accessToken -o tsv)

curl -X POST \
  "https://graph.microsoft.com/v1.0/servicePrincipals/$MI_OID/appRoleAssignments" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d "{\"principalId\":\"$MI_OID\",
       \"resourceId\":\"$GRAPH_ID\",
       \"appRoleId\":\"$ROLE_ID\"}"
Admin Consent automático para MI: o App Role Assignment via Graph já aplica o consent — não precisa do passo adicional como no SP.
Site Collection

🏢 Grant no Site Collection — POST /permissions

  • Obter token de acesso ao Graph (az account get-access-token)
  • Resolver o Site ID a partir da URL do site
  • POST em /sites/{site-id}/permissions com o Client ID do SP ou MI
  • Verificar com GET /sites/{site-id}/permissions
Client ID ≠ Object ID. No campo application.id do /permissions use sempre o Client ID (appId), nunca o Object ID / principalId.
Quem pode fazer o grant: Site Collection Administrator do SharePoint. Não precisa de Global Admin — só admin do site. 
TOKEN=$(az account get-access-token \
  --resource https://graph.microsoft.com \
  --query accessToken -o tsv)

# 1. Resolver site ID
SITE_ID=$(curl -s \
  "https://graph.microsoft.com/v1.0/sites/
   {tenant}.sharepoint.com:/sites/financeiro" \
  -H "Authorization: Bearer $TOKEN" \
  | jq -r '.id')

# 2. Conceder leitura ao SP ou MI
curl -s -X POST \
  "https://graph.microsoft.com/v1.0/sites/$SITE_ID/permissions" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "roles": ["read"],
    "grantedToIdentities": [{
      "application": {
        "id":          "<CLIENT_ID do SP ou MI>",
        "displayName": "indexer-app"
      }
    }]
  }'

# 3. Verificar
curl -s \
  "https://graph.microsoft.com/v1.0/sites/$SITE_ID/permissions" \
  -H "Authorization: Bearer $TOKEN" \
  | jq '.value[].grantedToIdentities'
Managed Identity

🪪 User-Assigned vs System-Assigned MI

CaracterísticaUser-Assigned (UAMI)System-Assigned (SAMI)
Client ID ✅ Conhecido antes do deploy ❌ Gerado apenas no deploy do recurso
RBAC / grants antecipados ✅ Pode configurar KV, Sites.Selected antes de criar o container ❌ Precisa do deploy para obter o principalId
Ciclo de vida Independente — persiste se o container for excluído Amarrado — excluiu o recurso, excluiu a MI
Reutilização ✅ Pode ser anexada a múltiplos containers / VMs ❌ Exclusiva do recurso onde foi criada
Troca sem downtime Troca o attach no container — código não muda Recria o recurso inteiro
Recomendação: sempre User-Assigned. O Client ID conhecido antes do deploy permite criar todos os grants (Key Vault Secrets User, Sites.Selected, AI Search roles) em IaC/scripts antes do primeiro deploy. 
# Criar UAMI
az identity create \
  --name mi-indexer \
  --resource-group rg4spo

# Capturar IDs necessários
az identity show \
  --name mi-indexer --resource-group rg4spo \
  --query "{clientId:clientId,
             principalId:principalId}"

# Resolver site ID
def get_site_id(token, site_url):
    host, path = _parse_url(site_url)
    r = requests.get(
        f"https://graph.microsoft.com/v1.0/sites/{host}:{path}"
        "?$select=id,displayName",
        headers={"Authorization": f"Bearer {token}"})
    r.raise_for_status()
    return r.json()["id"]

# Encontrar drive (biblioteca) pelo nome
def find_drive_id(token, site_id, library):
    r = requests.get(
        f"https://graph.microsoft.com/v1.0/sites/{site_id}/drives"
        "?$select=id,name",
        headers={"Authorization": f"Bearer {token}"})
    drives = r.json()["value"]
    drive = next(d for d in drives if d["name"] == library)
    return drive["id"]
# Listar arquivos .txt na raiz da biblioteca
def list_txt_files(token, drive_id):
    r = requests.get(
        f"https://graph.microsoft.com/v1.0"
        f"/drives/{drive_id}/root/children"
        "?$select=id,name,file",
        headers={"Authorization": f"Bearer {token}"})
    items = r.json()["value"]
    return [i for i in items
            if "file" in i and i["name"].endswith(".txt")]

# Baixar conteúdo do arquivo
def download_text(token, drive_id, item_id):
    r = requests.get(
        f"https://graph.microsoft.com/v1.0"
        f"/drives/{drive_id}/items/{item_id}/content",
        headers={"Authorization": f"Bearer {token}"},
        timeout=60)
    r.raise_for_status()
    try:
        return r.content.decode("utf-8")
    except UnicodeDecodeError:
        return r.content.decode("latin-1", errors="replace")
Graph API · Metadados

🏷️ Baixar metadados — campo Depto

$expand=listItem($expand=fields) retorna os metadados de coluna da lista subjacente ao drive em uma única chamada. Sem $expand, os campos personalizados ficam ocultos. 
# Listar arquivos COM metadados de colunas da lista
def list_files_with_meta(token, drive_id):
    r = requests.get(
        f"https://graph.microsoft.com/v1.0"
        f"/drives/{drive_id}/root/children"
        "?$select=id,name,file"
        "&$expand=listItem($expand=fields("
        "$select=Depto))",
        headers={"Authorization": f"Bearer {token}"})
    items = r.json()["value"]
    result = []
    for item in items:
        if "file" not in item: continue
        fields = (item.get("listItem") or {}).get("fields", {})
        item["depto"] = fields.get("Depto", "") or ""
        result.append(item)
    return result

Estrutura da resposta

{
  "id":   "01XYZ...",
  "name": "relatorio-q1.txt",
  "file": { ... },
  "listItem": {
    "fields": {
      "Depto": "Financeiro",
      // outros campos se solicitados
    }
  }
}
$select=Depto dentro do $expand limita a resposta apenas ao campo necessário — evita trazer todos os campos de sistema (Modified, Created, Author, etc.). Adicione outros campos separados por vírgula: $select=Depto,Autor,Ano
Nome do campo: é o internal name da coluna no SharePoint, não o display name. Para descobrir: GET /sites/{id}/lists/{list-id}/columns?$select=name,displayName
Checklist

📋 Checklist — Service Principal

Entra ID & Credencial

  • Criar App Registration (az ad app create --display-name sp4spo)
  • Criar Service Principal (az ad sp create --id <APP_ID>)
  • Adicionar App Role Sites.Selected (az ad app permission add ...)
  • Admin Consent (az ad app permission admin-consent --id <APP_ID>)
  • Gerar certificado no Key Vault (az keyvault certificate create)
  • Exportar .cer e vincular ao SP (az ad app credential reset --cert)
  • Conceder Key Vault Secrets User ao runtime (MI ou usuário dev)

SharePoint & Runtime

  • Resolver Site ID com GET /sites/{host}:{path}
  • Fazer grant no site: POST /sites/{id}/permissions com roles:["read"] e application.id = <CLIENT_ID>
  • Verificar: GET /sites/{id}/permissions
  • Definir no ambiente: SP_CLIENT_ID, SHAREPOINT_TENANT_ID, KV_CERT_NAME, AZURE_KEYVAULT_URL
  • Testar autenticação: obter token Graph e resolver site_id
  • Testar download: listar arquivos + baixar conteúdo + verificar metadados
Checklist

📋 Checklist — Managed Identity (mesmo tenant)

Entra ID & MI

  • Criar UAMI (az identity create --name mi-indexer --resource-group rg)
  • Anotar clientId (para grants) e principalId (Object ID do SP da MI)
  • Obter SP do Graph + Role ID de Sites.Selected via az ad sp show
  • Fazer App Role Assignment: POST /servicePrincipals/{mi_oid}/appRoleAssignments
  • Conceder Key Vault Secrets User à MI no KV (se usar KV para outros segredos)

SharePoint & Runtime

  • Resolver Site ID com GET /sites/{host}:{path}
  • Fazer grant no site: POST /sites/{id}/permissions com roles:["read"] e application.id = <MI_CLIENT_ID>
  • Verificar: GET /sites/{id}/permissions
  • Anexar UAMI ao Container App / VM / Function
  • Definir no ambiente: MI_CLIENT_ID=<clientId da UAMI>
  • No código: ManagedIdentityCredential(client_id=MI_CLIENT_ID) → get_token("https://graph.microsoft.com/.default")
  • Testar download e metadados
